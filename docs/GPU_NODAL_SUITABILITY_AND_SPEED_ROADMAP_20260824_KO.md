## 1. 질문: 노달 계산 자체가 GPU에 부적합한가?

**결론: 아니다. 부적합한 것은 알고리즘이 아니라 "단일 8,451노드 2군 문제의 크기"다.**

### 근거 1 — 단일 문제는 GPU의 ~2 %만 채운다

KNGR 쿼터 = 313×27 = 8,451노드, NG=2. RTX PRO 6000의 스레드슬롯(~수십만)에 대해
단일 인스턴스 CMFD는 **~8.7천 스레드 = 슬롯의 약 2~3 %**. 커널당 일감이 수 µs 수준이라
계산 시간이 아니라 **커널 발사 지연이 지배**한다:

- 단일런 프로파일(83.6 s): CMFD drive 41.4 s(49 %) = **302,763 디바이스 콜 × 137 µs/콜**
- 즉 CMFD 시간의 대부분이 "GPU가 계산하는 시간"이 아니라 "GPU를 호출하는 시간"

### 근거 2 — 일감을 채우면 같은 커널이 잘 돈다

64덱 배치 아레나(M64)에서는 동일한 노달/CMFD 커널로:
- GPU0 이용률 **78~93 %**
- 처리량 196.2 cases/h — 폴백 0, bit-exact 유지
- 자기 CPU 대비 압도적 우위 (단일 CPU런 175.8 s × 64 = 극단적 차이)

### 근거 3 — 문헌의 노달 GPU 성공 사례는 모두 "큰 문제"

- VANGARD: 노달 SENM/SP3 계열 41–89× — 전노심 세분격자·다군 구성
- KTH(arXiv:2501.09398): 소형 워크로드는 그래프 반복 배칭으로 >1.4×, 2–3배칭에서 교차
- 즉 노달 GPU화의 성패는 **문제 크기 × 배칭 전략**의 함수이며, 소형 문제의 정답은
  "포기"가 아니라 "집계(aggregation)와 발사 횟수 절감"

### 근거 4 — 단일런 격차의 절반은 GPU 문제가 아니다

같은 181 CPU에서: **RASBERY CPU 98.6 s vs MASTER 27.2 s (≈3.6×)**.
반복수·수렴 정책·구현 성숙도에서 오는 순수 알고리즘 헤드룸이 GPU 이전에 존재한다.
GPU를 붙이기 전의 기저 성능부터 MASTER와 같은 급이 아니라는 뜻이며, 이는 GPU
적합성과 무관하게 회수 가능한 영역이다.

## 2. 단일런 속도 확보 로드맵 (현 88.9 s → 목표 30 s대)

우선순위 순. ①이 가장 큰 단일 레버이며 병렬(M64)에도 동시에 기여한다.

### ① Outer 전체 그래프화 (최우선)

- 현재: 내부 BiCG 루프만 그래프(스윕 단위 발사) → 런당 30만 콜
- 목표: **outer 1회 반복 전체를 CUDA Graph 1발사로 캡처** + 디바이스측 수렴 판정으로
  D2H 동기 최소화
- 기대: 발사 횟수 ~10배 절감 → CMFD 41 s 중 지연 성분이 한 자릿수 s로
- 제약: Wielandt 갱신·halt 게이팅이 이미 디바이스에 있으므로 구조적 준비는 끝나 있음.
  bit-exact 체계(fma 마스크, 고정청크 리덕션) 유지 필수 — 그래프화는 연산 순서를 바꾸지
  않으므로 원리적으로 무해

### ② CPU 잔류 스테이지 이관 (= 저자 B/D단계와 동일 항목)

단일런 기준 잔여 호스트 비중:

| 스테이지 | 비중 | 조치 |
|---|---|---|
| setls (CMFD 행렬조립) | 8.9 % | GPU 배치화 (B단계) |
| IO write (HDF5) | 6.0 % | writer 스레드 분리 (D단계) |
| upddhat | 5.5 % | GPU 배치화 (B단계) |
| updjnet | 1.8 % | 〃 |

### ③ CPU–GPU 오버랩

TH 갱신·CBC 탐색 로직(호스트 전담)을 GPU 스윕과 스트림 중첩. 현재는 순차 실행.

### ④ 알고리즘 헤드룸 분석 (GPU 무관, 2~3× 여지)

MASTER가 동일 물리를 CPU 27.2 s에 푸는 요인 분해:
- outer/inner 반복수 비교 (수렴 정책, Wielandt shift 파라미터)
- 상태점당 재계산 범위 (XS 재구성 빈도, TH 커플링 횟수)
- 필요 시 MASTER 수렴 기준에 맞춘 "동등 정확도 모드" 신설 검토

## 3. 병렬(M64) MASTER 초과 로드맵 (현 196 → 218 돌파 → 300+)

### 1단계: 218 돌파 (MASTER W16 추월)

- **B단계 — CMFD 조립(setls/upddhat/updjnet) GPU 배치화**: 호스트 경로가 짧아지면
  도착 스큐가 줄어 **집계 폭(현 22.0/64)이 상승하고 이득이 곱해진다**.
  캠페인 검증 원칙: *"폭은 대기(linger)로 살 수 없고 호스트 경로 단축으로만 산다"*
  (노달 FULL 이관 때 실증: 스큐 7,955→4,388 µs → 폭 16→22.7)
- **D단계 — HDF5 writer 스레드 분리**: M64에서 락 대기 2.7 %(734 ms/획득)
- 예상: 두 항목으로 218 돌파 현실적

### 2단계: 월등한 우위 (300+ cases/h)

- **슬롯 128 확장**: 현 max RSS 18.8 GB → 128슬롯 ≈ 38 GB (서버 램 확인 필요).
  GPU 이용률 78~93 %에 아직 여유가 있고, 발사당 집계 폭이 커질수록 지연 상각이 개선
- **①의 outer 그래프화**가 병렬에도 그대로 기여 (인스턴스당 발사 횟수 절감 → 랑데부
  오버헤드 감소)
- (참고) 재활용워커 경로(A24)를 고속화하려면 refcount 기반 unpin 레지스트리 후속 필요
  — 현재는 정확성만 확보(pageable, 99.2 cases/h)
- (제약) GPU1은 타 사용자 전용이므로 2-GPU 확장은 대상 외

### 비교 기준 주의

MASTER W16(216–218)은 181 PC CPU 기록치로 동일 하드웨어 정면 비교가 아니다.
"각 코드의 현실 운용 구성" 비교이며, 동일 서버 CPU에서 MASTER를 재실측하면 기준선이
달라질 수 있다.

## 4. 권고 실행 순서

1. **outer 전체 그래프화** (단일런 + M64 동시 이득, 최대 레버)
2. B단계 (CMFD 조립 GPU화) → M64 218 돌파 확인
3. D단계 (HDF5 writer 스레드)
4. 슬롯 128 실험 (램 확인 후)
5. 알고리즘 헤드룸 분석 (MASTER 반복수 비교) — 단일런 30 s대 진입의 마지막 조각

각 단계마다 골든 bit-exact 게이트(500/500) + M64 처리량 회귀를 통과해야 채택한다.
