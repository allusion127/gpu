# v3 동결 준비 — 생산 arm, 게이트 등급, 계기 중립성 (2026-08-29)

계획 Rev.7.1 Task 22의 1차 항목("v3 동결 · 검증 · Draft PR")을 위한 준비 문서다.
**이 문서는 동결이 아니다.** 동결에 필요한 것 — 생산 구성이 무엇인지, 각 구성요소가
어떤 등급으로 통과했는지, 238에서 무엇이 측정되었고 무엇이 아직 아닌지, 되돌리는
방법이 무엇인지 — 을 한 곳에 모으고, 러너가 채울 매니페스트 골격
(`test/reference/validation_baseline_manifest_v3.json`,
`validation_thresholds_v3.json`)을 함께 둔다.

**코드 기본값은 하나도 바뀌지 않는다.** v3 arm의 네 구성요소는 모두 env로만 도달하며,
env를 설정하지 않은 실행은 v2 궤적 그대로다. 롤백이 "env 하나를 지우는 것"인 이유가
이것이고, §7이 이를 구성요소별로 적는다.

---

## 1. v2가 무엇을 동결했고, v3가 왜 필요한가

v2(2026-08-27, `e64794f`)는 **기본값 외 비-기본 구성요소가 하나뿐인** 단일덱 실행의
궤적을 동결했다 — 호스트 Anderson Xe. 그것은 최적화가 아니라 **수렴 결함의 수정**으로
채택되었고(불수렴 Xe 인공물 ~2–3 pcm 제거), MASTER 일치가 1.970 → 1.905 pcm으로
**좋아졌기 때문에** 동결이 정당했다.

Rev.7.1 캠페인이 도달한 생산 구성은 그보다 넷 많다. 그중 셋은 **구성상 궤적을 바꾼다**:

- 청크 Wielandt 접기와 device Xe Anderson 대수는 **리덕션의 결합 순서를 바꾼다**.
- A2 단계화 허용오차는 **수렴 도중 무엇으로 수렴하는지를 바꾼다**(발행되는 답은
  여전히 생산 허용오차에서만 나온다 — §3의 A2 행 참조).

각각은 이미 개별 게이트를 통과했다. **v3는 넷을 함께, 한 번, 재는 지점**이며 그
결과가 이후 모든 Gate A의 기준이 된다.

## 2. 생산 구성 (v3 arm)

```bash
# 실행 기반 — arm X (S2 + XSRECON/FLATXS)
export RASBERY_GPU=1
export RASBERY_GPU_CMFD_SWEEP=1
export RASBERY_GPU_CMFD_RESIDENT_SINGLE=1     # S2
export RASBERY_GPU_NODAL=1 RASBERY_GPU_NODAL_FULL=1
export RASBERY_GPU_XSRECON=1 RASBERY_GPU_FLATXS=1
export RASBERY_OMP_THREADS=12

# device outer 세그먼트 (B0)
export RASBERY_GPU_OUTER=1 RASBERY_GPU_OUTER_SEGMENT_MAX=8

# N1 구성요소
export RASBERY_GPU_WIEL_FOLD=chunked
export RASBERY_GPU_XE=1

# A2 채택 후보 (N1)
export RASBERY_STAGED_FLUX_TOL=50
export RASBERY_STAGED_XE_TOL=1000
export RASBERY_STAGED_LOOSE_SETTLE=1

# 설정하지 말 것
#   RASBERY_XE_ANDERSON        — 단일 실행 기본값 ON 이 검증 대상이다
#   RASBERY_STATEPOINT_TELEMETRY — 타이밍 반복과 섞지 말 것 (§6.3)
```

`--rasi kngr_238.json`, 단일덱. 배치(`--batch-mode`)는 **이 동결에 포함되지 않는다**(§5).

### 2.1 실행이 자기 arm을 증명한다 (신규)

이번 커밋부터 모든 실행이 마지막 줄에 **게이트 없이** 다음을 찍는다:

```
[RASBERY][TRAJECTORY] {"schema_version":1,"slot":0,"statepoints":35,"outers":4602,
  "th_updates":126,"digest":"decdf6e767d476f2","telemetry":0,
  "env":{"RASBERY_GPU_XE":"1","RASBERY_STAGED_FLUX_TOL":"50",...}}
```

- `digest` — 상태점별 (step, outer, T/H, efpd·k_eff·붕소의 **비트 패턴**)의 접기.
  요약이 아니라 궤적 자체다. 같은 arm의 두 실행은 정확히 일치하고, outer 하나 또는
  k_eff 마지막 비트가 움직인 실행은 일치하지 않는다.
- `env` — 궤적을 움직일 수 있는 모든 knob의 **원시 문자열**(미설정은 null).
  해석하지 않는 것이 요점이다: 승수를 재-해석하는 수신증은 SolveLoop의 해석과
  어긋날 수 있고, 이 줄이 절대 하면 안 되는 일이 그것이다.
- `telemetry` — 디제스트 **밖에** 있다. 이 분리가 §6.4의 게이트를 가능하게 한다.

동결된 baseline의 `digest`는 매니페스트 `golden_outputs.trajectory_digest`에 들어간다.
v3 재현을 주장하는 후보는 이 digest를 찍어야 한다.

## 3. 구성요소별 게이트 등급

| 구성요소 | env | 등급 | 근거 | 게이트 |
|---|---|---|---|---|
| S2 resident-single | `RASBERY_GPU_CMFD_RESIDENT_SINGLE=1` | **B0** | 같은 커널, 같은 순서, 상주만 다름 | bit 동일 (644/644), 55.2 → 48.7 s |
| device outer 세그먼트 | `RASBERY_GPU_OUTER=1` `_SEGMENT_MAX=8` | **B0** | 호스트 outer 본문과 bit-identical; 호스트 사다리가 여전히 권위 | feature-off byte 동일성 (h5diff 전 데이터셋) |
| 청크 Wielandt 접기 | `RASBERY_GPU_WIEL_FOLD=chunked` | **N1** | 접기 범위의 고정 분할 = 덧셈 결합 변경 | Gate A(v2) + Gate B(MASTER), `[CMFD][WIEL_FOLD] mode=chunked source=env` 수신증 필수 |
| device Xe Anderson | `RASBERY_GPU_XE=1` | **N1** | 6개 내적이 직렬 접기 → `k_xe_dot_reduce` 고정 분할. 대수·창·안전장치 4종·reset 엣지는 호스트 arm과 bit 동일(`tools/test_xe_gpu_contract.py`) | Gate A/B + **수용률 ±10 pp** + `[XE_GPU] host_fallbacks=0` |
| A2 단계화 허용오차 | `RASBERY_STAGED_FLUX_TOL=50` `_XE_TOL=1000` `_LOOSE_SETTLE=1` | **N1 (A2)** | 이동 중에는 느슨한 허용오차로 수렴. **느슨한 단계의 합의는 종료가 아니라 polish 단계의 방아쇠**이고, 생산 허용오차에서 얻은 합의만 solve를 끝낸다(`tools/test_staged_tolerance.py`가 이 불변식을 고정) | Gate A/B + `staged_relapses` 보고 |

**B0와 N1의 차이는 신뢰도가 아니라 게이트다.** B0는 "이전 경로와 비트가 같다"를
증명하면 끝이고, N1은 Gate A(크기 보고) + Gate B(MASTER 쪽으로 갔는지)를 요구하며
그 결과가 v3 동결의 내용이 된다.

### 4.1 데이터셋 수 불일치 — 동결 전 해소할 것

v2 매니페스트는 골든을 **500 데이터셋**으로 기록했다. 같은 덱에 대해 로컬 트리는

문제다: 644개를 담은 파일에 대해 "0/500"이라고 인용한 게이트는 144개를 보지 않은
게이트다. 동결 실행은 238이 실제로 비교하는 수를 기록하고, 그것이 500이 아니면 어느
커밋이 데이터셋을 늘렸는지 한 줄로 적어야 한다.

## 5. 배치는 이 동결에 포함되지 않는다

이유는 두 가지이며 둘 다 기존 측정이다.

1. **A2를 배치에서 켜지 말 것.** Anderson 배치 OFF와 같은 도착폭 기아 구조
   (캠페인 §8.2)에 걸린다. 배치 채택은 Phase 5 slot compaction 이후 별도 판정이다.
2. 배치 wall은 compute가 아니라 **I/O 직렬화**가 통제한다(SPTELEM 위상 분해에서
   io_wall이 단일덱 ~3 %에서 M64 ~40 %로 폭증). 단일덱 outer −70 %가 배치 처리량에
   그대로 나타나지 않는다.

따라서 v3는 **단일덱 동결**이다. 배치 골든은 v2(그리고 그 배치 규약)를 유지한다.

## 6. 동결 절차

### 6.1 빌드

```bash
cmake -S <repo> -B <bld> -DCMAKE_BUILD_TYPE=Release \
  -DRASBERY_ENABLE_CUDA=ON -DRASBERY_CUDA_ARCHITECTURES=120 \
  -DRASBERY_ENABLE_TESTS=ON
cmake --build <bld> -j
```

`compile_commands.json`에서 `arch=compute_120,code=[compute_120,sm_120]`과
`CudaXsReconBackend.cu`의 per-TU `--fmad=false`를 **확인해서 매니페스트에 적는다**
(v2가 그렇게 했다).

### 6.2 타이밍 반복 (텔레메트리 없이, ≥3 hot)

```bash
# §2의 env를 export 한 뒤
for r in 0 1 2 3; do
  /usr/bin/time -f "%e" -o $O/v3_r$r.wall \
    <bld>/RASBERY --rasi kngr_238.json --raso $O/v3_r$r.h5 > $O/v3_r$r.log 2>&1
done   # r0 은 warm-up, 버린다. wall 은 r1..r3 median
h5diff -r $O/v3_r1.h5 $O/v3_r2.h5     # 결정론: 전 데이터셋 0
h5diff -r $O/v3_r1.h5 $O/v3_r3.h5
grep TRAJECTORY $O/v3_r*.log          # digest 4개가 모두 같아야 한다
```

### 6.3 수신증 실행 (타이밍과 **섞지 말 것**)

```bash
RASBERY_STATEPOINT_TELEMETRY=1 <bld>/RASBERY --rasi kngr_238.json \
  --raso $O/v3_tel.h5 > $O/v3_tel.log 2>&1
python3 tools/outer_profile.py $O/v3_tel.log
```

### 6.4 계기 중립성 게이트 (신규, 필수)

```bash
python3 tools/test_telemetry_neutrality.py --compare $O/v3_r1.log $O/v3_tel.log
```

`env`가 다르면 그 쌍은 **텔레메트리 결과가 아니라 환경 차이**이며, 도구가 그렇게
말한다. `env`가 같고 `digest`가 다르면 계기가 solve를 움직인 것이고, 그것은 결함이다.

### 6.5 Gate A / Gate B

```bash
python3 tools/gate_a_compare.py $O/v2_baseline.h5 $O/v3_r1.h5 --per-step
python3 tools/compare_master_rasbery.py <MAS_SUM> $O/v3_r1.h5 -o $O/master_v3
# BOC 핀은 기존 핀 스크립트로 별도 산출
```

Gate A의 델타는 **0이 아닐 것으로 예상된다**(넷 중 셋이 N1). Gate A는 움직임의
**크기**를 보고하고, 그것이 MASTER **쪽으로** 갔는지는 Gate B만이 답한다 — Anderson
채택 때와 같은 구조의 질문이다.

### 6.6 부수 게이트

```bash
ctest --output-on-failure                       # 12/12
for t in tools/test_*.py; do python3 $t; done   # 사전 실패 4건 외 신규 실패 0
```

사전 실패 4건: `test_cmfd_fp32_contract.py`, `test_ga_feedback_screen.py`,
`test_ga_promotion_gate.py`, `test_nodal_constant_cache.py`.

### 6.7 매니페스트 채우기

`test/reference/validation_baseline_manifest_v3.json`과
`validation_thresholds_v3.json`의 `TBD_V3_FREEZE`를 전부 교체하고, **마지막 자리를
채우는 같은 커밋에서** 두 파일의 `frozen`을 `true`로 뒤집는다. v1/v2 파일은 이력으로
**손대지 않는다**.

## 7. 롤백

구성요소별이며, **재빌드가 필요 없다**.

| 되돌릴 것 | 방법 | 되돌아가는 곳 |
|---|---|---|
| A2 단계화 | `unset RASBERY_STAGED_FLUX_TOL RASBERY_STAGED_XE_TOL RASBERY_STAGED_LOOSE_SETTLE` | 생산 허용오차 단일 단계 |
| device Xe Anderson | `unset RASBERY_GPU_XE` | 호스트 Anderson (v2 궤적) |
| 청크 접기 | `unset RASBERY_GPU_WIEL_FOLD` | 직렬 접기 (v2 궤적) |
| device outer 세그먼트 | `unset RASBERY_GPU_OUTER RASBERY_GPU_OUTER_SEGMENT_MAX` | 호스트 outer 본문 (bit 동일) |
| S2 | `unset RASBERY_GPU_CMFD_RESIDENT_SINGLE` | 비상주 CMFD (bit 동일) |

네 env를 모두 지우면 v2 arm이며, 그 실행은 **v2 매니페스트에 대해** 게이트해야 한다.
코드 되돌림이 필요한 경우에만 각 구성요소의 feature 커밋을 revert 한다.

## 8. 계기 중립성 — 이번에 확인된 것

238에서 A2 후보가 **plain 3,114 outer / telemetry 4,393 outer**로 보고되었다
(base arm은 양쪽 10,483로 불변). 계기가 반복 횟수를 바꾼다면 계기가 보고하는 모든
수는 다른 실행에 관한 수가 되므로, 이것은 먼저 답해야 하는 질문이었다.

### 8.1 소스에는 결합이 없다

`RASBERY_STATEPOINT_TELEMETRY`의 소비자는 정확히 둘이다.

| 소비자 | 위치 | 하는 일 |
|---|---|---|
| `outer_timing::Scope` | `src/Driver.h:294-317` (`_local = sptelem::enabled()`) | 시계를 읽고 두 개의 위상 누산기에 더한다. `ctx.`도, `eigv`/`residual`/`prev_inner`/`clean_iters`/`flux_stall`도 만지지 않는다 |
| `Drive()`의 `sp_telem` | `src/Driver.h:3673` | 수신증 키 생성, 백엔드 카운터 스냅샷(읽기 전용), 줄 포맷 |

정착 게이트(`Driver.h:3383`)가 읽는 것은 `has_search` · `schedule.searchType` ·
`staged_loose_settle` · `polishing` · `clean_iters`뿐이고, 이 다섯 중 어느 것도
텔레메트리가 쓰지 않는다. `ctx.telemetry.*`는 전부 `++` 또는 `+=`이며 **어디에서도
읽히지 않는다**(`tools/test_statepoint_telemetry.py`가 이미 그 형태를 고정한다).
`tools/test_telemetry_neutrality.py`가 이 두 문장을 편집 시점에 고정한다.

### 8.2 로컬 실측: 8개 arm 전부 중립

1080 Ti / sm_61, 전체 kngr_238:

| arm | telemetry OFF | telemetry ON | h5 |
|---|---|---|---|
| base | 12,017 | 12,017 | 644/644 동일 |
| CAND, host Xe, OUTER on | 4,614 | 4,614 | 동일 |
| CAND, GPU Xe, OUTER on | 4,602 | 4,602 | 동일 (`[OUTER_GPU]` 수신증까지 바이트 동일) |
| CAND, host Xe, OUTER off | 4,614 | 4,614 | 동일 |
| CAND, GPU Xe, OUTER off | 4,602 | 4,602 | 동일 |

OUTER off 두 행이 중요하다 — device 세그먼트가 켜져 있으면 호스트 본문이 아예 돌지
않아 `outer_timing::Scope`가 실행되지 않는다(`host_body_calls.updpsi = 0`). OUTER를
끄면 Scope가 outer마다 돌고, **그래도 중립**이다.

### 8.3 남은 가설과, 그것을 가르는 방법

238 관측은 로컬에서 재현되지 않았고 소스에 결합이 없다. 남는 설명은 둘이다.

1. **두 실행의 env가 달랐다.** `docs/A2_OUTER_REDUCTION_20260829_KO.md` §6.2는
   CAND를 `export` 후 **맨 바이너리**로 돌리고 §6.3은 텔레메트리 실행을
   **인라인 env**로 돌린다. V3 env 집합이 한쪽 셸에만 export 되어 있었다면 두 실행은
   서로 다른 arm이며, base arm은 양쪽 env가 같았으므로 영향이 없다 — **관측된
   signature와 정확히 일치한다.**
2. 238에서만 나타나는 호스트 타이밍 의존 경로. 로컬에서는 8개 arm 어디에서도
   나타나지 않았다.

§6.4의 게이트가 이 둘을 가른다. 앞으로 이 질문은 두 줄의 grep으로 끝난다.

### 8.4 로컬 4,614 ↔ 238 3,114 은 Xe arm 때문이 아니다

동일 후보에 대해 **`RASBERY_GPU_XE=1` 단독으로 4,614 → 4,602**(−12, 0.26 %)일 뿐이다.
로컬과 238의 1,500 outer 차이는 GPU Xe arm도, 텔레메트리도 아니며,
**sm_61 ↔ sm_120에서 device 리덕션 형태가 달라 궤적이 갈린 것**이다(붕소 secant 탐색이
그 차이를 증폭한다 — `CMFD_OUTER_FORMS`가 양쪽 0x7이어도 분할·점유는 같지 않다).
즉 outer 수는 **호스트마다 다른 값**이며, `docs/A2_OUTER_REDUCTION_20260829_KO.md`
§6.3의 "238에서도 outer 수는 동일해야 한다(결정론적)"는 기대는 **B0 arm에서만
성립한다**. N1 구성요소가 켜진 arm에서는 성립하지 않으며, 그 문장이 238 조사를 잘못된
방향으로 보냈다. 판정은 outer 수의 절대값이 아니라 **같은 호스트 안의 A/B**로 해야
한다.
